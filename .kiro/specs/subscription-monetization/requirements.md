# Requirements Document

## Introduction

This feature adds a monetization and subscription system to the BibleFunLand Homeschool Hub. It introduces two tiers — **Free** and **Pro** — enforced at the pack-generation boundary. Free users may generate up to 3 worksheet packs per calendar month; Pro subscribers ($7.99/month) have unlimited generation. Stripe Checkout handles payment collection, Stripe Webhooks keep the Turso DB in sync, and the Stripe Customer Portal lets Pro users manage or cancel their subscription. A new `/pricing` page communicates the tier comparison. The generate page surfaces real-time usage for Free users. The profile page shows subscription status and a management link for Pro users. A designated admin user (identified by `ADMIN_USER_ID` environment variable) is always treated as Pro regardless of database state.

Additionally, this feature expands the preset Quick Templates on the generate page with at least 10 new diverse Bible story themes spanning Old and New Testament, covering all four grade ranges.

---

## Glossary

- **Hub**: The BibleFunLand Homeschool Hub Next.js application.
- **Subscription_System**: The server-side logic that enforces tier limits, manages Stripe integration, and exposes subscription status to the UI.
- **Free_Tier**: The default tier for all authenticated users who have not purchased a Pro subscription. Allows up to 3 pack generations per calendar month.
- **Pro_Tier**: The paid subscription tier at $7.99/month. Allows unlimited pack generation.
- **Generation_Limit**: The maximum number of packs a Free_Tier user may generate within a single calendar month (value: 3).
- **Usage_Counter**: The count of packs generated by a specific user in the current calendar month, derived from the `packs` table.
- **Subscription_Record**: A row in the `subscriptions` table representing a user's current subscription state.
- **Stripe**: The third-party payment processor used for checkout, webhooks, and the customer portal.
- **Stripe_Checkout**: The Stripe-hosted payment page used to collect payment and activate a Pro subscription.
- **Stripe_Webhook**: An HTTP POST from Stripe to `/api/stripe/webhook` that notifies the Hub of subscription lifecycle events.
- **Customer_Portal**: The Stripe-hosted self-service portal where Pro users can update payment methods or cancel their subscription.
- **Pricing_Page**: The `/pricing` page that displays the Free vs. Pro tier comparison and the Subscribe button.
- **Upgrade_Prompt**: The UI element shown to Free_Tier users who have reached their Generation_Limit, directing them to the Pricing_Page.
- **Admin_User**: The user whose Clerk user ID matches the `ADMIN_USER_ID` environment variable. Always treated as Pro_Tier.
- **Pack_API**: The set of Next.js API route handlers under `/api/packs`.
- **DB**: The Turso (libSQL) database accessed via `lib/db.ts`.
- **Auth_System**: The Clerk-based authentication layer.
- **Educator**: An authenticated user who creates and manages Packs.

## Requirements

### Requirement 1: Subscription Database Schema

**User Story:** As a system operator, I want subscription state persisted in the database, so that tier enforcement is consistent across sessions and server restarts.

#### Acceptance Criteria

1. THE DB SHALL contain a `subscriptions` table with columns: `user_id` (TEXT PRIMARY KEY), `stripe_customer_id` (TEXT), `stripe_subscription_id` (TEXT), `status` (TEXT — one of `active`, `canceled`, `past_due`, `trialing`), `current_period_end` (TEXT — ISO 8601 datetime), `updated_at` (TEXT — ISO 8601 datetime).
2. WHEN `ensureDB()` is called, THE DB SHALL execute `CREATE TABLE IF NOT EXISTS subscriptions (...)` before any subscription read or write.
3. IF the `subscriptions` table already exists, THEN THE DB SHALL leave the existing table and its data unchanged.
4. THE DB SHALL enforce `user_id` as the primary key so that each Clerk user has at most one Subscription_Record.

---

### Requirement 2: Subscription Status Resolution

**User Story:** As the system, I want a single authoritative function to determine a user's effective tier, so that all enforcement points use consistent logic.

#### Acceptance Criteria

1. THE Subscription_System SHALL expose a server-side function `getUserTier(userId: string): Promise<'free' | 'pro'>` that returns the effective tier for a given user.
2. WHEN `getUserTier` is called with a `userId` that matches `ADMIN_USER_ID`, THE Subscription_System SHALL return `'pro'` without querying THE DB.
3. WHEN `getUserTier` is called and the user has a Subscription_Record with `status = 'active'` and `current_period_end` in the future, THE Subscription_System SHALL return `'pro'`.
4. WHEN `getUserTier` is called and the user has a Subscription_Record with `status = 'trialing'` and `current_period_end` in the future, THE Subscription_System SHALL return `'pro'`.
5. WHEN `getUserTier` is called and no Subscription_Record exists for the user, THE Subscription_System SHALL return `'free'`.
6. WHEN `getUserTier` is called and the Subscription_Record has `status = 'canceled'` or `current_period_end` is in the past, THE Subscription_System SHALL return `'free'`.
7. THE Subscription_System SHALL expose a server-side function `getMonthlyUsage(userId: string): Promise<number>` that counts the number of packs the user has generated in the current calendar month by querying the `packs` table where `created_by = userId` and `created_at >= first day of current UTC month`.

---

### Requirement 3: Pack Generation Enforcement

**User Story:** As a Free Tier user, I want the system to enforce my monthly generation limit, so that the business model is protected and I understand when I need to upgrade.

#### Acceptance Criteria

1. WHEN `POST /api/packs` is called by an authenticated user, THE Pack_API SHALL call `getUserTier(userId)` before proceeding with generation.
2. WHILE the user's effective tier is `'free'`, THE Pack_API SHALL call `getMonthlyUsage(userId)` and compare it against the Generation_Limit of 3.
3. IF the user's effective tier is `'free'` and `getMonthlyUsage` returns a value greater than or equal to 3, THEN THE Pack_API SHALL return HTTP 403 with `{ "error": "Monthly generation limit reached", "upgradeRequired": true }`.
4. WHEN the user's effective tier is `'pro'`, THE Pack_API SHALL proceed with generation without checking the Usage_Counter.
5. THE Pack_API SHALL NOT apply the in-memory hourly rate limit (`rateLimitMap`) to Pro_Tier users.
6. IF `ADMIN_USER_ID` is not set in the environment, THEN THE Subscription_System SHALL treat no user as an admin (no bypass).

---

### Requirement 4: Usage Display on Generate Page

**User Story:** As a Free Tier user, I want to see how many packs I have used this month on the generate page, so that I can plan my usage and understand when I need to upgrade.

#### Acceptance Criteria

1. WHEN an authenticated Free_Tier user loads the generate page, THE Hub SHALL fetch `GET /api/subscription/usage` and display the result as "X of 3 free packs used this month".
2. THE Hub SHALL render the usage indicator as a progress bar or badge above the generate form, visible only to Free_Tier users.
3. WHEN the Usage_Counter equals 3, THE Hub SHALL disable the generate form submit button and display the Upgrade_Prompt in place of the button.
4. THE Upgrade_Prompt SHALL contain a message explaining the limit has been reached and a button linking to `/pricing`.
5. WHEN an authenticated Pro_Tier user loads the generate page, THE Hub SHALL display "Unlimited generation — Pro Plan" instead of a usage counter.
6. THE Hub SHALL expose `GET /api/subscription/usage` which returns `{ "tier": "free" | "pro", "used": number, "limit": number | null }` for the authenticated user.
7. IF `GET /api/subscription/usage` is called without a valid session, THEN THE Subscription_System SHALL return HTTP 401.

---

### Requirement 5: Pricing Page

**User Story:** As a visitor or Free Tier user, I want to see a clear comparison of Free and Pro tiers, so that I can make an informed decision about subscribing.

#### Acceptance Criteria

1. THE Hub SHALL render a `/pricing` page accessible to both authenticated and unauthenticated users.
2. THE Pricing_Page SHALL display two tier cards: one for Free_Tier and one for Pro_Tier.
3. THE Free_Tier card SHALL list: "3 packs per month", "Unlimited browse & print", "Access to all existing packs".
4. THE Pro_Tier card SHALL list: "Unlimited pack generation", "All Free features", "$7.99/month".
5. THE Pricing_Page SHALL display a "Subscribe — $7.99/month" button on the Pro_Tier card.
6. WHEN an unauthenticated Visitor clicks the Subscribe button, THE Hub SHALL redirect the Visitor to sign in before initiating Stripe_Checkout.
7. WHEN an authenticated Free_Tier user clicks the Subscribe button, THE Hub SHALL call `POST /api/stripe/checkout` and redirect the user to the returned Stripe_Checkout URL.
8. WHEN an authenticated Pro_Tier user views the Pricing_Page, THE Hub SHALL replace the Subscribe button with a "Manage Subscription" button that links to the Customer_Portal.
9. THE Pricing_Page SHALL be linked from the Navbar for all users.

---

### Requirement 6: Stripe Checkout Session Creation

**User Story:** As a Free Tier user, I want to be redirected to a secure Stripe payment page when I click Subscribe, so that I can safely enter my payment details.

#### Acceptance Criteria

1. THE Hub SHALL expose `POST /api/stripe/checkout` which creates a Stripe_Checkout session and returns `{ "url": "<stripe_checkout_url>" }`.
2. WHEN `POST /api/stripe/checkout` is called by an authenticated user, THE Subscription_System SHALL create or retrieve a Stripe customer for that user using the user's email from Clerk.
3. THE Subscription_System SHALL create a Stripe_Checkout session with `mode: 'subscription'`, the Pro_Tier price ID from `STRIPE_PRO_PRICE_ID` environment variable, `success_url` pointing to `/profile?subscribed=true`, and `cancel_url` pointing to `/pricing`.
4. THE Subscription_System SHALL attach the Clerk `userId` as metadata on the Stripe_Checkout session so that the webhook can identify the user.
5. IF `POST /api/stripe/checkout` is called without a valid session, THEN THE Subscription_System SHALL return HTTP 401.
6. IF the Stripe API returns an error during session creation, THEN THE Subscription_System SHALL return HTTP 500 with `{ "error": "Failed to create checkout session" }`.

---

### Requirement 7: Stripe Webhook Processing

**User Story:** As the system, I want to process Stripe webhook events to keep subscription state in sync, so that Pro access is granted immediately after payment and revoked when a subscription ends.

#### Acceptance Criteria

1. THE Hub SHALL expose `POST /api/stripe/webhook` that receives and processes Stripe webhook events.
2. WHEN a webhook request is received, THE Subscription_System SHALL verify the Stripe signature using `STRIPE_WEBHOOK_SECRET` before processing any event.
3. IF the Stripe signature is invalid or missing, THEN THE Subscription_System SHALL return HTTP 400 with `{ "error": "Invalid signature" }` and SHALL NOT process the event.
4. WHEN a `checkout.session.completed` event is received with `mode: 'subscription'`, THE Subscription_System SHALL upsert a Subscription_Record with `status = 'active'`, `stripe_customer_id`, `stripe_subscription_id`, and `current_period_end` derived from the Stripe subscription object.
5. WHEN a `customer.subscription.updated` event is received, THE Subscription_System SHALL update the Subscription_Record's `status` and `current_period_end` to match the Stripe subscription object.
6. WHEN a `customer.subscription.deleted` event is received, THE Subscription_System SHALL update the Subscription_Record's `status` to `'canceled'`.
7. THE Subscription_System SHALL extract the Clerk `userId` from the Stripe session or subscription metadata to identify which Subscription_Record to upsert.
8. WHEN a webhook event is successfully processed, THE Subscription_System SHALL return HTTP 200 with `{ "received": true }`.
9. IF an unrecognized event type is received, THEN THE Subscription_System SHALL return HTTP 200 with `{ "received": true }` without modifying any data.

---

### Requirement 8: Stripe Customer Portal Access

**User Story:** As a Pro Tier subscriber, I want to manage or cancel my subscription through a secure portal, so that I have full control over my billing without contacting support.

#### Acceptance Criteria

1. THE Hub SHALL expose `POST /api/stripe/portal` which creates a Stripe Customer_Portal session and returns `{ "url": "<portal_url>" }`.
2. WHEN `POST /api/stripe/portal` is called by an authenticated Pro_Tier user, THE Subscription_System SHALL retrieve the `stripe_customer_id` from the user's Subscription_Record and create a Customer_Portal session with `return_url` pointing to `/profile`.
3. IF `POST /api/stripe/portal` is called without a valid session, THEN THE Subscription_System SHALL return HTTP 401.
4. IF the user has no Subscription_Record or no `stripe_customer_id`, THEN THE Subscription_System SHALL return HTTP 400 with `{ "error": "No active subscription found" }`.
5. IF the Stripe API returns an error during portal session creation, THEN THE Subscription_System SHALL return HTTP 500 with `{ "error": "Failed to create portal session" }`.

---

### Requirement 9: Profile Page Subscription Display

**User Story:** As an educator, I want my profile page to show my current subscription status and a way to manage it, so that I always know my tier and can take action.

#### Acceptance Criteria

1. WHEN an authenticated Educator navigates to `/profile`, THE Hub SHALL fetch subscription status alongside profile data and display either "Free Plan" or "Pro Plan" as a badge in the profile header.
2. WHEN the Educator's effective tier is `'pro'`, THE Hub SHALL display a "Manage Subscription" button on the profile page that calls `POST /api/stripe/portal` and redirects to the returned URL.
3. WHEN the Educator's effective tier is `'free'`, THE Hub SHALL display an "Upgrade to Pro" button on the profile page that links to `/pricing`.
4. WHEN the profile page loads with `?subscribed=true` in the query string (redirect from successful Stripe_Checkout), THE Hub SHALL display a success banner: "Welcome to Pro! Your subscription is now active."
5. THE Hub SHALL update `GET /api/profile` to include `{ "tier": "free" | "pro" }` in its response alongside existing stats.
6. THE Hub SHALL display the subscription tier in the existing stats row on the profile page, replacing or augmenting the static "Educator" role badge.

---

### Requirement 10: Admin Bypass

**User Story:** As the admin user, I want to always have Pro access regardless of subscription state, so that I can test and demonstrate all features without a paid subscription.

#### Acceptance Criteria

1. THE Subscription_System SHALL read `ADMIN_USER_ID` from the server-side environment at runtime.
2. WHEN any tier check is performed for a user whose Clerk `userId` equals `ADMIN_USER_ID`, THE Subscription_System SHALL return `'pro'` without querying THE DB or Stripe.
3. THE Subscription_System SHALL NOT expose `ADMIN_USER_ID` as a `NEXT_PUBLIC_` variable or in any client-side code.
4. WHEN `ADMIN_USER_ID` is an empty string or undefined, THE Subscription_System SHALL not grant any bypass and SHALL treat all users according to their Subscription_Record.

---

### Requirement 11: Expanded Preset Templates

**User Story:** As a homeschool educator, I want a wider variety of preset Bible story templates on the generate page, so that I can quickly start packs for diverse Old and New Testament stories across all grade ranges.

#### Acceptance Criteria

1. THE Hub SHALL display at least 13 preset Quick Templates on the generate page (the existing 3 plus at least 10 new ones).
2. THE new preset templates SHALL include stories from both the Old Testament and the New Testament.
3. THE new preset templates SHALL cover all four Grade_Ranges: `Preschool-K`, `Grades 1-2`, `Grades 3-4`, and `Grades 5-6`.
4. EACH preset template SHALL include a descriptive `title`, a detailed `theme` prompt (specifying story reference, activity types, and a memory verse), and a `range` matching one of the four Grade_Ranges.
5. THE new preset templates SHALL include at minimum the following stories: Moses and the Burning Bush, The Good Samaritan, Jonah and the Whale, The Birth of Jesus (Nativity), Daniel in the Lions' Den, The Ten Commandments, The Prodigal Son, Esther Saves Her People, The Sermon on the Mount, and The Road to Emmaus.
6. WHEN an Educator clicks a preset template, THE Hub SHALL populate the theme input and grade range selector with the template's values, as the existing templates already do.

---

### Requirement 12: Security and Environment Variable Protection

**User Story:** As a system operator, I want all Stripe and subscription secrets to remain server-side only, so that payment credentials are never exposed to the browser.

#### Acceptance Criteria

1. THE Hub SHALL access `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_PRO_PRICE_ID`, and `ADMIN_USER_ID` exclusively within Next.js API route handlers and server-side modules.
2. THE Hub SHALL expose only `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` as a public Stripe environment variable, and only if client-side Stripe.js initialization is required.
3. WHEN the Stripe webhook handler processes a request, THE Subscription_System SHALL use the raw request body (not parsed JSON) for signature verification, as required by the Stripe SDK.
4. THE Subscription_System SHALL NOT log or return `stripe_customer_id`, `stripe_subscription_id`, or any Stripe secret values in API responses visible to the client.
